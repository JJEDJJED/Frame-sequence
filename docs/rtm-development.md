# 主体居中RTM

2026-10-23。第二套独立的人物居中方案，节点类型 `rtmCenter`，显示名称「主体居中RTM」。原「主体居中」继续使用 TAPNext；RTM 不读取它的选点或轨迹。

## 目标和中心定义

RTMPose 每帧独立估计左右肩与左右髋。设双肩中点为 S，双髋中点为 H，采用中心为 `S + r × (H - S)`，默认 `r = 0.5`，可在属性面板调整至 0～1。这个定义以躯干为基准，避免跟随转身时外观消失的胸部纹理，也避免武器、头发、刀光扩大外接框后移动中心。

四个关节都必须满足分数、坐标、前景与肩髋长度检查才会直接采用。内部缺失区间按各帧时长插值，首尾缺失保持最近可靠中心；全部不可用则保留原图位置。插值与保持帧始终提示检查。模型分数是 SimCC 响应值，不是概率；低分帧仍显示实际最低分，便于判断拒绝原因。

每帧仅执行整数平移。用所有非零 Alpha 内容确定统一画布并对称扩展，避免裁掉独立光效和淡光；最后使用最终画布中心计算全部偏移。采用中心相对数学中心的误差不超过 0.5 像素。这是像素取整误差，不代表识别人体中心的误差。

## 模型与隔离环境

- Python 3.12.13，仓库 `.venv/`，由 uv 与 `uv.lock` 管理。
- ONNX Runtime 1.31.0，OpenCV Headless 4.14.0.94，本次使用 CPU，最多 4 个推理线程。
- 官方 [RTMPose 模型库](https://github.com/open-mmlab/mmpose/tree/main/projects/rtmpose#-model-zoo-) 的 RTMPose-m Human-Art，17 点，输入 192×256；[Human-Art 数据集](https://github.com/IDEA-Research/HumanArt) 包含多种艺术人物形式。
- [官方模型压缩包](https://download.openmmlab.com/mmpose/v1/projects/rtmposev1/onnx_sdk/rtmpose-m_8xb256-420e_humanart-256x192-8430627b_20230611.zip) SHA256：`e2b38e3a585d013eb2002259f8ca1b16543bf35ad499cf3b6ba4f2254294d8fe`。
- 提取的 ONNX SHA256：`12e1b9fcbcd867c3fb6d8f4d509cf1d8c5373df5e529676e32f6dd888758316c`。

`npm run rtm:setup` 安装 `rtm` 可选依赖组，下载并核验压缩包，只提取明确指定的模型及配置文件，将来源和摘要写入 `.models/rtmpose/provenance.json`。权重、环境、测试项目均忽略入库。安装时保留另一方案的依赖；RTM 工作进程不加载 PyTorch / TAPNext 模型。

预处理按官方 pipeline：最大有效 Alpha 连通区域确定输入 ROI，边界扩展 1.25 倍并调整到 3:4；透明像素合成灰底，RGB 按官方 mean/std 归一化。这个区域只设置模型分辨率，不参与输出中心计算。SimCC 使用 split ratio 2，不做 softmax / DARK / 翻转增强；每个关节分数取 x、y 峰值的较小值，与 [MMPose 官方解码](https://github.com/open-mmlab/mmpose/blob/main/mmpose/codecs/utils/post_processing.py) 一致。将预测坐标映射回原图后，检查半径 2 像素区域的前景 Alpha。

## 接口和缓存

Node 经 JSONL 管道调用独立 `python/rtm_worker.py`，不增加监听端口。第一次非空帧任务加载模型，后续任务复用；取消会结束该工作进程，下次任务重建。全透明帧不运行模型。

- `GET /api/rtm/status`
- `POST /api/projects/:pid/rtm`
- `GET /api/projects/:pid/rtm/:jobId`
- `DELETE /api/projects/:pid/rtm/:jobId`

RTM 继承已有任务服务的进度、取消与项目隔离，采用独立 `estimate` 操作，不需要 query points。保持来源 / 请求头保护，并只解析当前项目的素材。重复启动检查两套接口；旧后端缺少 RTM 时明确提示重启。Windows 的重复启动分支使用 `process.exitCode`，让状态请求清理完毕后退出，避免强制退出触发 libuv handle 断言。

缓存保存原始关键点、分数、前景标记、模型信息和输入内容指纹。求值不自动触发推理；阈值和中心比例变化直接复用缓存，源图内容、帧顺序或尺寸变化会停用缓存。推理完成时再次检查当前源，避免将异步旧结果写到新素材。

## TDD 和验证

先添加缺失模块导致失败的测试，再实现模型适配、居中几何、独立节点与 HTTP 服务。几何测试包含旋转躯干、异常关节、透明区域、按时长插值、全部失败原图输出与阈值重算；节点测试验证像素平移、元数据与源图变更；服务测试验证独立操作、项目隔离和旧服务诊断。浏览器发现低分帧误显示 0 分，以及清空姿态后异步求值完成前预览异常，均先用回归测试复现失败，再修复并验证通过。

本次验证结果：

- Node：66 项通过，包含 RTM 与原跟踪流程。
- 普通 Python：20 项通过，3 项真实模型测试默认跳过。
- 另行开启 RTM 真实模型测试：通过。合成人物平移 `(17, 8)` 后，肩髋坐标随之平移，误差在测试的 1 像素容差内。
- 99 个 JavaScript 文件语法检查、Ruff、uv 锁文件离线一致性检查通过。

实际 24 帧素材通过浏览器在独立项目副本中执行真实 CPU 推理：原图 309×165、8fps、每帧 130ms，默认阈值 0.25，20 帧采用肩髋估计，第 4、15、16、17 帧使用插值。第 9 帧采用原图中心 `(108.56, 50.67)`，骨架位于躯干区域；此前 TAPNext 曾偏至头发位置约 `(124.57, 45.08)`。这组结果没有人工逐帧中心真值，不将它作为所有动作精度的结论。

浏览器验证了开始识别、骨架与中心线、逐帧回退提示、修改中心比例、阈值重算、刷新复用姿态、清空及撤销恢复、烘焙输出。烘焙的 24 张 PNG 与原图按预期整数偏移平移后的 RGBA **逐像素一致**；输出 309×167，帧数、8fps、每帧 130ms 保持，所有非零 Alpha 内容均未裁切。采用中心的最大取整误差为 0.4921875 像素，替换轮廓框不影响中心或偏移。

本次测试没有改写用户原项目。低分插值、保持或高分误识别仍需查看骨架；单人物透明动画是当前适用输入，未实现多人身份关联或三维人体中心恢复。
